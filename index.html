How I build

The same principles guide every product I work on.

Built for local realities

I consider how people and businesses actually operate in Nigeria, from Naira pricing and bank transfers to WhatsApp-based communication and data protection.

Designed for reliability

I build with failure in mind, using background jobs, retries, and safeguards against duplicate requests where they matter. A slow network shouldn't turn a simple action into a costly mistake.

Tested for production

I review my code for security, reliability, performance, and maintainability, then fix the issues I find before deployment. The goal is software that's not just functional, but dependable.

Engineering notes

Migrations behind a connection pooler

PgBouncer in front of PostgreSQL can't run schema changes reliably, so migrations use their own direct database URL while the app connects through the pooler. I also resolved SCRAM and MD5 authentication mismatches between the two.

Latency to a hosted database

Slow queries and slow health checks on Vitar traced back to the distance between the server and a hosted database in a faraway region. I tuned both.

Audits before and after launch

Repeated audit rounds on Vitar closed unauthenticated analytics endpoints, fixed a misconfigured Celery health check and tuned connection pool sizes.

Messages that aren't lost or doubled

On Wabizz, Cloudflare Queues deliver messages, dead letter queues catch failures and idempotent jobs stop a retry from processing the same message twice.

Rate limits and failing providers

Rate-limit counters are sharded across Durable Objects to spread load, and circuit breakers isolate a failing provider so one outage doesn't spread.

Tests you can inspect

The Wabizz repository includes Playwright end-to-end tests, Vitest unit tests and a load-testing folder, all public on GitHub.
